# Decision log

Decisions made while building that refine or depart from [architecture.md](architecture.md) or the [build plan](build-plan.md). Each entry says what, why, and what else was considered.

## Phase 0

**Bundled fonts include Source Sans 3 Italic.** The plan named Regular, Semibold and Bold. matplotlib's maths typesetting needs an italic face configured even when labels are set upright, so the Italic is bundled as well (316 KB). Alternative considered: fall back to matplotlib's DejaVu italic, which would mix typefaces. Light and Medium are bundled too, so every weight a theme can name (light, regular, medium, semibold, bold) is available.

## Phase 1

**Review pages and the catalog are exempt from the large-file check.** They are self-contained HTML files with embedded images (architecture D6), so they routinely exceed the 600 KB limit that guards against accidentally committed binaries. The exemption applies only to `review/` and `catalog/`.

**The deny-list check skips embedded base64 images.** Review pages and the catalog embed images as base64 text, which can contain a short deny-listed term purely by chance (a review page did). The contents of `;base64,` data are skipped; all other text is still checked.

**Series labelling is a set of methods, chosen per theme.** The architecture described one direct-label algorithm with a legend fallback. Review of the spike set the rule that labels sit inside the plot, beside their own series, touching nothing, and then that labelling should be a set of methods: each theme allows some, in order of preference, and `labels: auto` uses the first that fits. First methods: `interior`, `legend`, `none` (specs/chart-type.md §5). End-of-line labels, margin labels, `matplotlib-label-lines` and `adjustText` were tried and rejected (review/phase-01/spike-findings.html).

**Filters are structured conditions; aggregation and binning sit on each field.** Specified in specs/graphspec.md §3–4. Structured conditions need no parser, map one-to-one onto Studio's filter shelf and translate directly into SQL. Per-field aggregation (the Tableau and Vega-Lite model) makes grouping implicit and keeps every GraphSpec representable on shelves. Alternative considered: expression strings for filters, which need a parser covering strings, dates, relative dates and quoting.

**GraphSpec structure, from review of the GraphSpec spec.**
- **Version field:** `forgegraph: 1` becomes `spec_version: 1`. It versions the format, not the software, whose version goes in provenance.
- **Graph type:** `chart` becomes `graph_type`, and "graph type" replaces "chart type" everywhere: `graph_types/<name>/graph_type.yaml`, docs/specs/graph_type/xy.md.
- **Required fields:** `graph_type` and `data` are always required. A DataFrame from Python is a source (`dataframe: <name>`).
- **Two sections:** data roles go under `columns:` and drawing choices under `options:`, instead of sitting flat beside the common fields. The definition files use the same names.
- **Presets:** a preset is its own document (`preset: <name>`, a description, saved settings, no data), not a GraphSpec without data.
- **Theme option defaults:** these move to their own section, keyed by graph type or `all` (renamed `variable:` below).

**Themes and formats, from review of the style spec.**
- **Parameters:** a theme's parameters are the style parameters (grouped by the part of the graph they affect and named so they explain themselves, e.g. `tick.label_size`, `plot_box.sides`) and each graph type's look options (`xy.mode`, `xy.labels`; marked `theme_parameter` in the graph-type file, with no default there). Options tied to one graph's data (axis titles, limits, benchmark) are GraphSpec-only.
- **Fixed and variable:** a theme lists each parameter under `fixed_parameters` (GraphSpecs using the theme can't change it) or `variable_parameters` (they may, under `options:`; the theme gives the default). A theme that extends another inherits each parameter it doesn't list, fixed or variable as it was there; a theme that extends nothing lists every parameter.
- **Graph-type sections:** parameters at the top of a section apply to every graph type; a graph type's name used as a category holds that type's own look options and any overrides. The nearest theme in the extends chain that gives a parameter decides it; within one theme the graph-type entry beats the general one. A general option must suit every graph type that has it.
- **Marker fills:** `series.marker_fills` is a list given to line_style_by groups in order, like the marker shapes.
- **Sizes:** every size in a theme is a multiple of the format's base font.
- **Grid:** the grid switch is the style parameter `grid.show` rather than a graph-type option, so `grid` names one thing.
- **Formats:** one file per format, every field present (only `description` may be blank); width and height each a length or `auto`, not both `auto`; `base_font` a number of points; output png, jpg, tiff, svg or pdf. Built-ins start with `slide-single` and `slide-double`, lengths in mm, provenance `full`, so published figures stay traceable.
- **Default format:** the GraphSpec spec alone says which format applies when none is set.
- **Spec examples:** the doc shows only the files; what each example is and which real file it must match is listed in tests/test_spec_docs.py. Invalid examples are followed by "ForgeGraph reports:" and the errors. Comments sit ten spaces after the text, and every YAML file and example uses four-space indents.

**YAML layout, from review of the specs.** Every file and example steps by four spaces. In graph-type and layer files, columns, options and gallery examples are mappings keyed by name, `style_parameters` maps each parameter to `always` or a condition, and `changelog` maps a version to its change, so entries nest like a theme's categories instead of sitting in lists. A GraphSpec's layers are a mapping keyed by name too, each with its type. Where a list remains (filter conditions, rules), each item's content starts four spaces after the dash. Sections (`data`, `source`, `columns`, `options`) are always indented blocks; braces are kept only for one-line values such as a filter condition or an `active_when` condition.

**The specification is four default files.** Theme, format, graph type and GraphSpec are each specified by one default file with the same layout: name, version, description, extends, then fixed\_parameters and variable\_parameters holding categories of parameters, each `name: default          # [RANGE]; DESCRIPTION`. The code reads every definition from those files and tests check it at the edges of every range. The earlier prose specifications (docs/specs) were deleted. Not yet in the default files, and added later as further specs: layers (reference lines, notes), presets beyond GraphSpecs that extend GraphSpecs, data filters, derived columns, binning and aggregation, asymmetric error bars, and custom color scales. Where a rule couldn't be a range, it was designed out: one source\_type plus source replaces "exactly one source", fixed one-value parameters replace prose rules, and nested settings became their own category (interior\_label). Two rules remain in code and are stated in the descriptions: a format's width and height can't both be auto, and a graph type's series\_labels must be one of the theme's series\_label.methods.

**Specification review, round 1.** No default graph type: xy is the first graph type, and the GraphSpec is specified by an example graph that sets every parameter. Header lines carry ranges like any parameter. Arbitrary limits became open ranges (positive number, positive int, int), and multipliers end in \_mult. Parameters with one allowed value were removed; missing values became a real choice (drop or gap). A parameter defined as None with no None in its range is required. Each axis names its data column and error column; grouping, marks and naming replace the old drawing category; line\_style\_by became style\_by. Data loading left the GraphSpec: the graph code receives a DataFrame, and a data source spec is proposed for later. Error bars are a layer, specified with the other layers: layers can come from the data too (a reference line at the mean, a fitted curve per series), so error bars aren't a special case. Their look stays in the theme's error\_bar category.

**Specification review, round 2.** "float" and "positive float" replace "number". In xy, each axis has a data\_column; grouping holds line\_style\_by, marker\_shape\_by, marker\_fill\_by (each its own column) and line\_path\_by; lines and markers each have show, replacing mode, and missing values belong to lines. A benchmark is a column and a value, drawn in the theme's benchmark\_style (color, line, marker). For titles, None means no title and the reserved word column\_name uses the column's name. The theme's per-group lists are singular (line\_style, marker\_shape, marker\_fill). A data source spec, named by a GraphSpec the way it names its theme, is to be written with scheduled graphs (phase 8); until then a graph is drawn from a DataFrame it's given.

**Data source spec, phase 2.** A data source is a fifth kind, defined by the example data\_sources/polarization.yaml: file path and type, Excel sheet, header row, rows to skip, encoding, missing-value markers and date columns. Every parameter is fixed, so a GraphSpec can't change how a file is read. A GraphSpec names its data source in specifications.data\_source; None means the graph is drawn from a DataFrame it's given. Use: graphs that are redrawn, shared or scheduled; one-off analysis passes a DataFrame.

**Drawing behaviour settled while building xy (phase 2).** A graph with one series isn't named, since its axis title already says what it is. Groups sort the way people read them: numbers in text by value ("6 cm2" before "130 cm2"). The benchmark has its own style, so it doesn't take a series color: the other groups start at the first color. With several y columns, y\_axis.title must be text or None: column\_name is refused, because there's no single name and a warning could go unseen by an agent. When line\_style\_by, marker\_shape\_by or marker\_fill\_by sets styles apart from the colors, a style key explains them at a clear position; if two different columns set styles, the key shows the first and a warning says so. Figures are laid out once before interior labels are placed, then the layout is frozen so the axes can't move under the labels. The snapshot and the data fingerprint describe the rows actually plotted.

**Invalid requests are errors, never silent substitutes (Steven, phase 2).** If what's asked is logically invalid or impossible, ForgeGraph stops and names the parameter and what to do, rather than defaulting to other behaviour or only warning (a warning can go unseen by an agent). Checked before drawing: several y columns with y\_axis.title or a column\_name legend title that has no single name; lines and markers both hidden; an axis min not below its max; a log axis limit at or below 0; a theme font that isn't available (matplotlib would substitute one); an Excel sheet on a text file, or a text encoding on an Excel file. Checked when drawing: a benchmark value matching no rows; a log axis over zero or negative data; a labelling method chosen by name that doesn't fit, auto with nothing that fits, or a style key with no clear position. Two different styling columns each get their own key. Behaviour the spec defines isn't a fallback: colors repeating past the last, as series.colors says, stays a warning.

**Forgemark's command-line tool is pinned.** Forgemark 1.10.0 delivered both of ForgeGraph's requests: the tool as a release file with a checksum, and `reattach --all`, which puts comments back after a page is regenerated (by element id, or by text, using the recorded surroundings when a passage repeats). forgegraph/catalog/forgemark.py (run directly as scripts/forgemark.py) downloads the pinned version once into the user's cache folder, checks its SHA-256 and runs it with Node. The catalog build, scripts/build\_recreations.py and scripts/mirror\_specs.py keep stored comments and run `reattach --all` after every rebuild. Problems found in Forgemark are reported to its maintainer, not worked around silently: 1.10.1 fixed text in adjacent HTML elements running together; 1.11.0 keeps a comment in an HTML page inside the element it was made in; 1.12.0, the pinned version, makes `reattach --all` require a copy's surroundings to match across its whole row, paragraph or list item, so a comment never moves to another copy of its text.

## Phase 3

**The catalog.** `forgegraph catalog build` writes catalog/forgegraph_base.html, generated from the specification files alone. Its layout (Steven, phase 3): the title; tabs for each kind (Themes, Formats, GraphTypes, Layers); tabs for each built-in file of that kind; the heading "Kind > name"; the parameter table (parameter, default, allowed values, status, description), in categories and subcategories that open and close, closed at first but open where a comment is; then the cards. The first card is the baseline: the example GraphSpec drawn from the example data source. Every other card is "Baseline + category.parameter = value", the baseline with exactly that change. A parameter that acts only once something else is set starts from a numbered baseline, "Baseline N: Baseline + category.parameter = value", and its card reads "Baseline N + category.parameter = value". The page has no other text. Every card is one change: a parameter that acts only in some setting starts from a numbered baseline with that setting (Steven, phase 5). Only a parameter that a rule ties to another gets one card listing both changes ("Baseline + benchmark.data\_column = None + benchmark.value = None"; a tick algorithm of manual and its step; the base axis and the axis columns). Baselines that need more than a parameter: the watermark cards start from "Baseline N: Baseline + non-standard drawing" (a line drawn with matplotlib after ForgeGraph finished), and the axis-extension card from a second example data source, fanned, whose curves all end at the same current. Only parameters that don't change the drawing (output file types, dpi, provenance) have no card. The example data's column names are the titles a reader should see ("Cell Current (mA/cm²)"), and the example GraphSpec titles its axes with column\_name. IBM Plex Serif (OFL) is bundled beside Source Sans 3 so font.family has a card: it has every weight a theme can use. The perturbation test draws every card and checks it differs from its baseline. The example GraphSpec leaves its axis limits automatic and draws one line per cell and run, so it varies cleanly. `forgegraph catalog check` (and a test) compares the page's recorded hash of the definitions, drawing code and version with the current ones.

**Drawing checks every file it uses.** Drawing a GraphSpec validates the graph type, theme, format and data source it names, and each file they extend, so a theme with a problem stops the graph rather than being drawn with substitutes.

**Font weights.** A theme's weights are font-file weights (light 300, regular 400, medium 500, semibold 600, bold 700). A theme whose font lacks a weight it uses is an error naming the weights the font has, rather than matplotlib substituting the nearest.

**Log axes** label ticks as plain numbers (0.001 to 99999) or as powers of ten, never both on one axis; within one decade they use ordinary steps, within three 1-2-5 steps.

**Default theme:** series.marker\_fill is [filled, open], so marker\_fill\_by shows its groups.

**Fixed while building the catalog:** with several y columns, each y column is its own line even when a line\_path\_by column is set (they were joined into one zigzag line).

**Extending the x-axis for labels adds no ticks:** the extra room holds labels only, so no tick label falls outside the area the layout made room for.

**Visual changelog.** scripts/visual\_changelog.py writes before and after images of every regression baseline and catalog figure that changed between two commits.

**Catalog files (Steven, phase 3).** Each theme, format and graph type has a catalog file, catalogs/themes/<name>.yaml, catalogs/formats/<name>.yaml or catalogs/graph\_types/<name>.yaml, the same in ForgeGraph, a pack or a project. It keeps the specification files' header and comment style, with a baseline line (the GraphSpec every card changes), baselines (numbered baselines: the baseline with one or more changes, or non-standard) and variations (every parameter's card value: a value, {value, from, with}, or no\_card). A catalog extending another lists only what differs. The build reads them and nothing else: no card values are held in code. Errors, all reported together: a missing catalog, a parameter missing or unknown, a value outside its range, a from naming no numbered baseline, a numbered baseline that isn't parameters and their values, and a card that draws the same as its baseline. A layer type's catalog, catalogs/layers/<type>.yaml, also gives settings (GraphSpec parameters every card sets so the layer can be drawn) and the layer every card draws; its baseline card names both. `forgegraph catalog build --project <folder>` adds a project's files and catalogs.

**Default look, round 1 (Steven).** The default format's height is auto (the plot box keeps plot\_box.aspect) and its base font 18 pt. Tick labels: a y label's digits are centred on its tick, and the new theme parameter tick.label\_gap\_mult sets the gap from a tick to its label's digits on both axes (matplotlib measured both from a text box that reaches well above the digits). A colour bar is exactly the plot box's height, so an auto figure size can't stretch it. Tests draw at their own fixed size (150 × 140 mm, 12 pt), so tuning the defaults doesn't change what they check.

**Text is measured to its letters (Steven, phase 3).** Matplotlib spaces text by a box sized for the font's tallest letters and deepest descenders, so its gaps aren't the gaps you see. Following the CSS `text-box: trim-both cap alphabetic` convention, Figma's vertical trim and D3's axis offsets, a text's edges run from the font's capital height to its baseline and grow only where its letters reach further (superscripts, descenders). Rows of text share one set of edges; collision checks use the letters themselves. forgegraph/drawing/text.py measures; drawing/spacing.py sets the tick-label, axis-title and title gaps from it; drawing/figure.py lays the figure out itself (no matplotlib layout engine), placing the plot box so what's drawn sits a fixed margin from each edge; drawing/key.py draws legends and style keys. New theme parameters: title.gap\_mult, axis\_title.gap\_mult; legend title\_align, frame\_width\_mult, padding\_mult (one value for every side), title\_gap\_mult, row\_gap\_mult, handle\_length\_mult, handle\_gap\_mult, inset\_mult; color\_bar width\_mult and gap\_mult (its ticks and title use the axes' settings); watermark weight, angle and span (it is centred on, and fitted to, the plot box); tick.minor\_num, minor\_length\_mult and minor\_width\_mult.

**Default look, round 2 (Steven).** Legend rows and the title-to-first-entry gap are about half what they were, the sample-to-name gap 20% less, and the legend title is left-aligned. series.marker\_edge\_width\_mult is 0.06. interior\_label.max\_axis\_extension is a limit: the x-axis grows by the least that fits the labels. The example GraphSpec titles its color bar by column.

**Default look, round 3 (Steven).** Roboto (SIL Open Font License) is the default font, chosen from a comparison of 13 open fonts. Major ticks on linear axes come from a published algorithm chosen by tick.algorithm (drawing/ticks.py): extended\_wilkinson (Talbot, Lin & Hanrahan 2010, the default), wilkinson, heckbert, nelder (AS 96), r\_pretty or matplotlib; each gets a target label count from the axis length. Text is drawn without font hinting, so it has the same width at every resolution and what's laid out is what's saved; the box lines' half-widths count in the layout's visible extent, so the figure's margins are exact.

**Parameter names and the catalog page, round 4 (Steven).** Parameters nest in categories and sub-categories to any depth (a mapping inside a category is a sub-category); no path is a prefix of another, across kinds. No parameter name says \_mult: every size, width, length and gap is × figure.base\_size. The scheme: theme font, background, title, axis (title, tick, tick.label, tick.minor), plot\_area, grid, series (line, marker, benchmark), legend (label, direct, key, color\_bar), error\_bar, watermark; format figure, output, provenance; graph type axis (x, y), encoding (color, line\_style, marker\_shape, marker\_fill, detail, order), benchmark, mark (line, marker), legend (method, key.title.text, color\_bar.title.text). Where a standard term exists it follows Vega-Lite (encoding, mark, detail), keeping ForgeGraph's nesting, snake\_case and units; Vega-Lite's names weren't adopted wholesale, since a third of the parameters have no equivalent there. "Legend" is the umbrella for every way of naming what colors and styles mean (Vega-Lite's usage); the legend methods are direct, key and none, chosen by legend.method within the theme's legend.methods. series.colors is a named palette (color\_blind, Tableau's Color Blind palette; tableau\_10; okabe\_ito; tol\_bright; tol\_muted) or a list of hex colors. legend.color\_bar.layout places a color bar's title: title\_above (the default), title\_along (reading downward, its baseline facing the bar) or below (a horizontal bar under the x-axis title). The catalog page writes allowed values tersely (float > 0, int ≥ 0, float, 0-1, hex color code, alternatives separated by |, None last, lists in []), has no baseline-value column, groups each table by category, and shows cards only for variable parameters; the perturbation test still draws every card in the catalog files. The default format saves at 600 dpi, and its output.file\_types is variable (default [png]).

**Default look, round 4 (Steven).** title.size 1.05; series.line.width and series.benchmark.line.width 0.15; filled markers have a black outline 0.05 × base size wide; the benchmark is grey (#808080).

**fg.xy() keywords match the specification (Steven, phase 3).** color, line\_style, marker\_shape, marker\_fill and detail set encoding.color, encoding.line\_style, encoding.marker\_shape, encoding.marker\_fill and encoding.detail.

## Phase 4

**The command is `forgegraph` (Steven, phase 4).** `fg` is a built-in command in bash and zsh (job control), and a shell runs its built-in before any program of that name, so `fg render` never reached ForgeGraph from a terminal. The skill evals found it. One name, the package's own, rather than a second short alias.

**Lint v1.** Lint runs on every render, on the finished figure, and reports issues without changing the drawing: overlapping-text, clipped-text, key-over-data, too-many-groups (colors, line styles, marker shapes or fills repeating), log-axis-values, outside-limits, small-text (under 6 pt, the smallest text journals accept in print), font-fallback and dropped-rows. `Graph.check()` lints again after the figure has been drawn on. `forgegraph render --json` returns the issues as `lint`.

**ForgeGraph's input is a DataFrame (Steven, phase 4).** ForgeGraph takes a pandas DataFrame, passed through the Python API or read from the Parquet file a GraphSpec's `data.file` names (an absolute path, one starting with `~`, or one relative to the folder of the GraphSpec file that sets it), and draws it as the GraphSpec, theme, format and graph type say. A DataFrame passed through the API is drawn instead of `data.file`. How the DataFrame was made and where its file is kept are up to the user and the agent; `data.preprocessing` can say where the code that made it is, and is recorded in provenance, never read. The skill starts from the DataFrame. The catalog lists graph types, themes, formats and ForgeGraph's own GraphSpecs to extend. Data sources, `forgegraph inspect`, `render --snapshot` and the file loader are gone; phases 5, 6, 7, 8 and 12 follow (build plan).

**The CLI** has `render`, `catalog`, `schema` (`schema graphspec --graph-type --theme --format` lists every parameter a GraphSpec can set, with its range and description), `explain`, `load` and `skill install`. `catalog graph-types`, `catalog themes`, `catalog formats` and `catalog graphspecs` list one kind each (Steven). With `--json`, every error comes back as JSON `problems`, never a traceback. `render` names its files after the GraphSpec's file with only `.yaml` removed, so a dot in the name stays (`t_e0.25.yaml` saves `t_e0.25.png`). A parameter category at the top of a file, outside `variable_parameters`, gets an error saying where it goes.

**Dates on the x axis** get calendar ticks and concise date labels; the axis's offset label (a date axis's year) counts in the layout and in lint. The offset label takes its date from the first tick inside the data; matplotlib's takes the last tick's, which can fall after the data ends (Steven, phase 4).

**The skill (Steven, phase 4)** lives in the package (skill/forgegraph/: SKILL.md and examples/, an xy GraphSpec with its Parquet file) and is installed by `forgegraph skill install` into ~/.claude/skills, or a project's .claude/skills with `--project`; an installed copy that differs is replaced only with `--force`. SKILL.md says what a graph consists of (GraphSpec, graph type, theme, format), names the commands, and gives six steps: select or prepare the DataFrame as a Parquet file; select the graph type, theme and format (`default` if unclear); write the GraphSpec, structured like the examples; render and check the lint and the image; iterate until the graph meets the request and shows the data well; save the GraphSpec, graph and Parquet file to the user's folder, if there is one. The agent doesn't create or change themes or formats unless the user asks, and says so when a fixed parameter stands in the way. Parameter names, ranges and descriptions come from `forgegraph schema` at run time, never from the skill, so they can't drift; a test renders every packaged example. Tested with fresh Claude Code sessions (Opus, Sonnet, Haiku) on monthly CO2 data: every run made a correct graph.

**Skill evals** (evals/skill/cases.yaml, scripts/run_skill_evals.py) run each case through Claude Code in print mode, in a fresh project folder outside the repository, and grade it by script: the resolved GraphSpec values, a clean lint on redrawing, that the graph was made with ForgeGraph and looked at, files made, one GraphSpec kept across turns, and the data files unchanged.

**The default theme leaves more to the GraphSpec (Steven, phase 4).** Variable, so a GraphSpec can set them: series.line.width, series.marker.size, series.marker.edge\_width, series.benchmark.line.style, series.benchmark.line.width, series.benchmark.marker.size, legend.direct.clearance, legend.direct.max\_relative\_distance, legend.direct.max\_axis\_extension and legend.color\_bar.colors, as well as grid.show. Key samples have their own variable marker size, legend.key.sample.marker\_size (default 0.5, as series.marker.size), so shrinking the plot's markers for dense data leaves the key readable. Agents in the skill tests needed smaller markers and thinner lines for dense data.

**Numeric colors (Steven, phase 4).** `encoding.color_type` chooses how encoding.color's values pick colors: `categorical` (a palette color per value, named by the legend), `continuous` (a color scale with a color bar; the column must be numbers) or `auto` (continuous for a numeric column, categorical otherwise). With lines shown, a line joins only points of one color, so a numeric color column on the color bar draws one line per value; with markers only, points aren't split.

**Naming series (Steven, phase 4).** A graph's legend.method must be one of the theme's legend.methods, and `forgegraph schema graphspec --theme X` lists only theme X's. A single series is named like any other, unless its name is the y-axis title's text (the default, since both come from the y column), when the title already names it.

**The default palette is okabe\_ito (Steven, phase 4).** With 4 or more groups, color\_blind's colors ran together in the skill evals: two blues and two greys (review/phase-04/palette-comparison.html). Okabe and Ito's palette, designed for color-blind readers, keeps its first four colors distinct.

**The layout always fits its tick labels.** The layout lays out, measures the room needed around the plot box, and repeats until a pass changes the figure's size by under 0.001 in and moves the box by under 0.0001 of the figure. Tick labels can keep it from settling: a taller box gets more, wider labels, which make it shorter again. After 6 unsettled passes it lays out once more with, on each side, the most room either of the last two passes needed: an alternation has both its states there, so whichever labels the final draw has fit. Earlier passes, made while the figure was far from its size, don't count; including them left too little room on a graph that was settling slowly. Ticks are cleaned of float noise by rounding to decimal places that suit their step, not to whole multiples of it, which merged ticks that start off a multiple (1950, 1970… became 1960, 1960…).

**Log-axis ticks come from published algorithms (Steven, phase 4).** The theme's axis.tick.log\_algorithm picks one: breaks\_log (the default), a port of R's scales::breaks\_log (ggplot2's default for log axes; MIT licence, notice in drawing/ticks.py), or matplotlib, matplotlib's LogLocator (powers of ten only). breaks\_log's target number of breaks is how many ticks the theme's linear algorithm places across the axis's log10 range; where it gives up (an axis within one power of ten), the linear algorithm places the ticks. On either, the labels must fit: while the drawn labels would overlap or come within the tick-label gap of each other, the algorithm is asked for one tick fewer. This replaced a rule of ForgeGraph's own (1-2-5 steps within three decades), whose labels ran together on short axes in the skill evals.

## After phase 4

**The watermark belongs to the theme's author (Steven).** A GraphSpec can't change the watermark, since its parameters are fixed in the theme; a theme's author can restyle it however they like, even out of sight. An organisation that wants it required keeps those parameters fixed in its own theme. Its text must have at least one visible character, since it's drawn from its letters' outlines; a theme whose text has none is an error.

**The figure checks itself.** A ForgeGraph figure is a GraphFigure on a GraphCanvas (drawing/figure.py). Whatever draws or saves it, ForgeGraph or matplotlib directly (`figure.savefig`, a notebook showing the figure), first checks whether it's still as rendering left it: the same artists, drawing the same pixels (a hash of the figure drawn at its own size and resolution). A graph found changed stays non-standard, and every drawing of it carries the watermark, which sizes itself to the plot box each time it's drawn. Every save embeds the provenance record, through one function per file type's carrier (drawing/export.py), unless the caller sets the carrier's own key, as the catalog does to keep its images free of metadata.

**provenance: off keeps the non-standard flag.** With off, a standard graph's files carry no record; a non-standard graph's carry `level: off`, the ForgeGraph version and `nonstandard: true`, so they can still be told apart. `forgegraph load` reports such a record and can't recover a GraphSpec from it.

## Phase 7

**A layout only arranges GraphSpecs (Steven).** A layout holds what's particular to several graphs together: its format (size and output), its tabs, each a grid of GraphSpec files, and the separators between tiles. It has no theme, no title, no text tiles and no per-tile settings: text and style live in GraphSpecs, so a tile drawn alone and in a layout is the same graph. Panel labels, axes shared between tiles and one legend for several tiles are deferred until the rest is built and used.

**The grid is a list of tile names per row (Steven).** `areas: [[voltage, polarization], [hfr, polarization]]`, written one row under the other so it reads as a picture of the figure. A name repeated over a rectangle of cells spans it; `.` is blank. This is how CSS grids, matplotlib's subplot\_mosaic and patchwork describe layouts; a list of tiles with spans can't express a tile spanning rows. A grid whose rows differ in length, a name that doesn't fill a rectangle, an all-blank row or column, a tile not in the grid, and a grid name without a tile are errors.

**A tab's name is what its tab shows (Steven).** There's no separate label: file names and links use the name lowercased, spaces as hyphens ("By instrument" gives lab\_throughput-by-instrument.png and #by-instrument). Two tabs that would give the same file names are an error. A layout's tabs replace those it inherits, rather than merging by name as a GraphSpec's layers do: a set of tabs is one design.

**Spacing between tiles is the layout's (Steven).** It was proposed for the theme, as house style; but spacing between graphs exists only in layouts, and a layout has no theme. A pack can set its house spacing in a base layout that its others extend.

**The layout's format replaces each tile's.** Every tile is drawn at the layout's base size and the figure is the format's size; `forgegraph explain` shows each tile's format values as coming from the layout. With the format's height auto, each row is as tall as the tallest plot box its tiles' plot\_area.aspect asks for; row\_heights with an auto height is an error, since the aspects set the heights (and the same for width). Tiles are never shrunk to fit: a figure too small is an error naming the tiles that don't fit.

**HTML for GraphSpecs too (Steven).** html is a file type for any graph, not only dashboards: a graph linked from a wiki, or a scheduled graph whose page will show the stale banner. Figures are SVG with their text as outlines, so pages look the same in every browser.

**Example formats stay examples.** The journal-double and dashboard formats live in the phase 7 deliverable, not in ForgeGraph: sizes differ by journal and screen, and organizations keep their formats in packs.

**Bars on a date axis.** Bars placed their dates as raw nanoseconds, which crashed drawing; they now use matplotlib's day numbers, as lines do, so weekly bars draw and the bar-width check reports bars too wide for their weeks.

**Date axes: one calendar unit per axis (Steven).** Matplotlib's automatic date ticks mixed units (its 14-day step is the 1st and 15th of each month, labelled "Aug" and "15") and named the ticks' shared context in a corner ("2026-Jul") that could be a month no label showed. Now, as in d3 and Vega-Lite, ticks are a calendar unit's boundaries from a fixed list of steps (seconds up to centuries, with weeks on Mondays and months from January). auto takes the finest step whose labels fit, and never one finer than the data's spacing, so weekly data never gets daily ticks. Labels are at the ticks' unit (2026; Jul; Jul 6; 06:30), with the next unit up on a second line under the first tick and wherever it changes, as Plotly and Datawrapper do; there's no offset text. A given tick.label.format is used on every tick, with no second line. `datetime` is a data.type of its own (a column of dates or times only), tick.step takes weeks ("2 week"), the theme's fixed axis.tick.label.date_order writes days as Jul 6 or 6 Jul, and lint's dates-as-text reports a text column that reads as ISO dates, drawn as categories.

**Text of several lines is measured line by line.** Two-line date labels, wrapped tick labels and notes with line breaks are measured where each line sits, from matplotlib's own line layout; they had been measured as one line with a stray character, which left their upper lines out of the layout and lint.

## Phase 8

**A scheduled job is a schedule file (Steven).** Architecture D12 had the job as flags on `job install`. A file can be reviewed and kept in version control, `job run` reads it, and its cadence is checked like any other parameter.

**The cadence is an interval, a unit and when in it (Steven).** `interval` counts `interval_unit` (minute to year) and `at` says when in each unit, as one time or a list: ":30" for hours, "06:00" for days, "mon 06:00" for weeks, "1 06:00" for months, "Jan 1 06:00" for years; None is the unit's start. There's no second unit: launchd's calendar intervals, cron and Task Scheduler's repetition count whole minutes. A list replaces separate weekday settings (weekdays at 06:00 is a week with five times), and `interval` divides 60, 24 or 12 for minutes, hours and months and is 1 otherwise, since cron and launchd can't run every 2 weeks or 3 days exactly.

**The agent schedules `forgegraph job run` (Steven).** Whatever the environment offers runs `forgegraph job run <schedule>`: the machine's scheduler, a GitHub Actions workflow, a Claude scheduled task. The skill has the agent write the schedule file and schedule that command by the method of its choice. ForgeGraph doesn't write scheduler entries itself: that would reach only the local machine, so one user's path would differ from everyone else's and couldn't be tested as theirs, and each operating system's rules made it the brittle part.

**One target failing (Steven).** The others still render, each result is recorded, and the run exits 1. `on_failure` runs when any target failed and `on_success` otherwise, without a shell, with the job's name, status file and first error in its environment, and stopped after its timeout. on_success lets a check-in service notice a job that stopped running, which on_failure can't.

**Freshness (Steven).** "Data as of" is the data files' modification time: a target's oldest, so one stale tile makes a layout stale. It's drawn in every output as a footnote, in the theme's new fixed footnote category (small grey text at the bottom right, below everything else), with the cadence in words. HTML pages show a stale banner when the data is older than `freshness.stale_after_hours`; auto is the longest gap between runs plus 25 %, so a weekday job's Monday-morning page isn't stale. Stale data shows in the banner and the status file's data times, not through on_failure: a run that succeeds on old data isn't a failed run.

**Layouts default to the wide format (Steven).** The default layout's format is wide: the default format at 300 mm, so two columns are each as wide as one default graph, at the same 18 pt. At the default's 150 mm, two columns were too small for their labels in the skill evals, and a 2×2 grid couldn't be drawn at all. A one-column layout names default, as the skill's example does.

**Date formats without leading zeros (Steven).** A date tick label format takes %-d, %-m and %-H ("Jan 7"), which ForgeGraph writes itself, since strftime's differ by platform. Weekly ticks stay on Mondays even when the data starts on another day: ticks counted from the data's first day would be unintuitive for the reader.

**A layout sets its format's variable parameters (Steven).** As a GraphSpec can, a layout can set the variable parameters of its format (output.file_types and provenance.level), so a dashboard can be saved as HTML without a format of its own. `forgegraph schema layout` lists them, and `forgegraph explain` shows the layout as their source.

## Phase 9 spec review

**The first release is small (Steven).** Features come from specific requests, not from guessing what users will want. Cut from phase 9: the callout, arrow, band, ellipse, region and delta layers; a graph type `status` field; the GitHub issue form; the maintainer triage skill and `forgegraph request --draft`. Annotations are built when someone asks for them.

**Feature requests go through the skill (Steven).** One line in SKILL.md points to references/requests.md: file a GitHub issue on ForgeGraph's repository, or, for a custom pack, at the address in its pack.yaml's `issues`. Agents already know how to write a feature request or bug report, so there's no form.

**The provenance record (Steven).** docs/specs/provenance lists the record by level, and a test checks it against what's written. minimal: the provenance level, the ForgeGraph version, the creation time, the GraphSpec as written (without data.file and data.preprocessing), each spec used by name and version, and whether the graph is non-standard. full adds every resolved value, the data's file and the preprocessing reference. off: no record, not even for a non-standard graph, whose watermark still shows. Row counts and the data fingerprint aren't recorded.

## Phase 6 spec review

**Packs are the only source of named specs (Steven).** A person or organization keeps the specs that must be used, for a project or for all work, in a pack. Every theme, format, GraphSpec, layout or schedule a file names comes from a pack, named `pack/name`; specs of one's own are a folder pack, and ForgeGraph no longer picks up themes and formats folders beside a GraphSpec. Graph types and layer types are code, so they're named without a prefix and always available.

**The config lists the packs that may be used (Steven).** `packs` is the config's one setting. With a folder config, a file may use only the packs it lists. A pack it lists that the main config doesn't is non-standard: it works, but whatever is drawn with it is watermarked, its record names the pack (nonstandard_packs), and every command that uses or shows it says so. This replaces the error a folder config listing such a pack used to be: someone who can't change their organization's main config can still make and try a pack, and a pack used by accident is labelled, not silent. It also replaces the earlier choice that a folder's config replaces the main one, which would let a folder drop an organization's pack. There's no per-request config: a request works on a GraphSpec, which already names its specs.

**Extending creates a new spec (Steven).** A spec that extends another may change any of its parameters, fixed ones included, so it isn't narrowing; it's usable only if its own pack is allowed.

**Configs restrict use, not access (Steven).** A drawn file may name only the allowed packs' specs. A pack's spec may extend, or name as a theme or format, any spec ForgeGraph can find: in a pack a config that applies lists, or in an installed pip pack, loaded when a spec names it. This replaces the earlier rule that a pack's specs may build only on their own pack's and forgegraph_base's. A GraphSpec setting variable parameters is the narrowing that's always allowed.

**No defaults; base specs (Steven).** A GraphSpec names its graph type, theme and format, and a layout its format; nothing supplies one when it's missing, and packs and configs set none. ForgeGraph's complete specs, which others extend, are the pack `forgegraph_base`: `base_theme`, `base_format`, `base_layout_format` (the wide format for layouts), `base_layout` and `base_schedule`.

**A pack.yaml has five fields (Steven).** name, version, description, issues (where requests about its specs go) and requires (the ForgeGraph versions it works with). Packs can hold schedules, so an organization that requires its packs can still schedule renders.

## Phase 6

**Where packs live.** ForgeGraph's built-in packs, forgegraph_base and forgegraph_base_2 (Steven), are folders inside the package (src/forgegraph/packs), and a config names them like pip packs; a new main config lists both. Graph types, layer types and their catalog files stay in the core. Fonts are the core's too, in src/forgegraph/fonts, so any theme can use them. The acme example is in examples/packs.

**The main config is ~/.config/forgegraph/config.toml on every platform (Steven).** One path is the easiest to document; Windows included. `FORGEGRAPH_CONFIG` names another file instead, which keeps evals and tests away from the machine's own and lets an organization point at a managed one.

**A main config by default (Steven).** When there's no main config, the first command that reads the configs writes one listing the built-in packs, and says so; it never overwrites one. pip can't run code when it installs a package, so it's written on first use.

**Folder configs (Steven).** A forgegraph.toml is a folder config, and the CLI's option is `--folder`: calling it a project's would assume how the folder is used.

**A pack's fonts are registered when it may be used (Steven).** The .ttf and .otf files in its fonts/ folder, so a house theme can name its own typeface.

**The record names each spec's pack version (Steven).** Each spec used is recorded by name and version, and a pack's spec with its pack's version too, so a file shows which release of a house style drew it.

**Every built-in pack has a catalog page (Steven); a custom pack needn't.** `forgegraph catalog build` builds ForgeGraph's (its graph types, layer types and the base pack); `catalog build --pack <folder>` builds a pack's, catalog/<pack>.html, from the catalog files in its catalogs/ folder. A pack's catalog draws from its own example GraphSpec, in its own format, so the cards show its theme at the sizes it's meant for; its catalog files extend the base pack's and list only what differs. Each catalog page is named for its pack (catalog/forgegraph_base.html, catalog/forgegraph_base_2.html) and shows its version under its title. A pack's page also shows ForgeGraph's graph types and layer types drawn in the pack's first theme and format, so a reader sees how each looks in it (Steven); a card that can't be drawn there shows ForgeGraph's message instead, since a pack can't change those cards.

**Plain names for specs made in code.** A theme or format added to a registry through the Python API has no pack and keeps the name it's given; only names written pack/name are checked against the configs.

**`forgegraph schema pack` and `schema config`** list a pack.yaml's fields and a config's settings, read from the base pack's pack.yaml and the reference config, so an agent asked to make a theme can make the pack and config that hold it. The skill's references/themes_formats_configs.md says how (Steven).

**An agent is shown only the allowed packs (Steven).** `forgegraph catalog` and `forgegraph pack-notes` show only the specs and reference notes of the packs the configs allow; `forgegraph schema graphspec` shows any spec ForgeGraph can find, so an agent can see how a spec it builds on is written. `pack-notes` prints every allowed pack's notes, each under its pack's name and version.

**Theme parameters to replicate a matplotlib style (Steven).** Built from his tableau_like style sheet: font.weight (text without its own weight: tick labels, value labels, notes, key names, footnotes), plot_area.line_color, series.line.cap and series.line.join, and legend.key.background. The base theme's values draw as before.

**forgegraph_base_2 follows the matplotlib output, not the style sheet's numbers.** Matplotlib drew the style's font weight 350 with Source Sans 3 Light, so the theme uses light. Its gaps were measured against the style's output (tick to label, label to axis title, title to plot area) and set to match, since matplotlib measures from text boxes and ForgeGraph from letters. The format is 106 mm wide, which gives the plot area matplotlib's 3.41 in at 4.4 in, and 200 dpi, as Steven asked; with no format parameters added, the image isn't cropped to its contents as `bbox: tight` crops it.

**Milestone 3 plan revisit (Steven).** The public release comes first. Before it, phase 6's real-data trial is replaced by a trial with the forgegraph_base_2 pack, run from a runbook. The trial on his company's data, which also files phase 9's one real request, and phase 8's week-long dashboard come after the release.

## Phase 9

**The blank canvas.** `forgegraph.blank(theme, format)` checks its theme and format against the configs as a GraphSpec's are. Its Axes cycles through the theme's palette, and drawing inside `with canvas.drawing():` gives what's drawn the theme's matplotlib settings. It's always non-standard: every drawing carries the watermark, and its record has no GraphSpec, its theme and format by name and version, and nonstandard: true.

**Public first, from a fresh repository (Steven).** The repository goes public before the release, so CI runs free on every push. The first two commits held a confidential term, so the public repository, sskaye/forgegraph, starts from the current files as one commit, without the earlier history; the private working history is kept as sskaye/forgegraph-dev.

**The first release is 0.1.0 (Steven).** Before it, the version is whatever is convenient.
